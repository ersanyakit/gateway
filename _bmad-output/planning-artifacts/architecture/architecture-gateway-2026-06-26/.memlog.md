- (direction by user) Product vision covers two customer surfaces: provide wallet infrastructure to exchanges and provide crypto payment acceptance to e-commerce merchants.
- (constraint) Existing repository is a Go Fiber v3, GORM, PostgreSQL monolith with merchant portal, admin portal, checkout, v1 API, blockchain listeners, ledger models, webhook notifier, sweep jobs, payout and refund flows.
- (constraint) Current audits classify merchant payment gateway as credible MVP, wallet provider as partial, and Binance-level exchange wallet tracking as not production-ready until signer, durable eventing, horizontal indexers, reorg accounting, reconciliation, and custody policy are implemented.
- (assumption) User likely wants the Architecture Spine plus a concise human-facing solution design for technical team or partner alignment; confirm during coaching if audience differs.
- (decision by user) Adopt modular-monolith-first architecture with event-driven money movement and explicit internal ownership boundaries; defer physical microservice split until money invariants, outbox contracts, signer isolation, and reconciliation are stable.
- (decision) Two product surfaces share one money core: Merchant Payment Gateway owns checkout/payment-session lifecycle, Exchange Wallet Provider owns user wallet/deposit/withdrawal lifecycle, and both consume the same Wallet, Chain Event, Ledger, Signer, Webhook, and Reconciliation boundaries.
- (decision) Ledger is the only authoritative balance source; chain transactions, sweep jobs, payment sessions, withdrawal requests, and refund records may reference money movement but must not calculate available balance independently.
- (decision) All money-affecting lifecycle changes are event-driven and idempotent: deposit, payment, withdrawal, refund, sweep, reorg, reconciliation, and webhook events must carry a stable event_id/idempotency key and version suffix.
- (decision) Chain Indexer is a source-of-facts component only: it owns block/transaction detection, chain state, provider health, finality signals, and reorg detection, but cannot mutate payment status or ledger balances directly.
- (decision) Signer boundary is mandatory before production custody: application services request signatures by key reference and policy context; mnemonic/private key material must not be returned, stored in app DB, or logged.
- (decision) Withdrawal and sweep flows require ledger hold/reservation before signing and chain-specific nonce or UTXO ownership before broadcast; retries must reconcile existing broadcast state rather than blindly creating replacement transactions.
- (decision) Webhook Service owns external delivery for all merchant and exchange lifecycle events, including payment, deposit, withdrawal, refund, sweep, and correction events; source services enqueue events and never deliver callbacks inline.
- (decision) Postgres outbox is the first durable event substrate inside the modular monolith; physical Kafka/NATS/SQS style brokers are deferred until outbox volume, replay, partitioning, and worker ownership requirements justify a split.
- (decision) Tenant model remains merchant/domain based in the current API but must be named as tenant/domain at architecture level so exchange tenants and e-commerce merchants can share auth, webhooks, ledger accounts, and wallet ownership rules.
- (decision) Production rollout is phased: harden current monolith, introduce modular package boundaries and outbox, split stateless workers first, then isolate Ledger/Wallet/Signer/Withdrawal, then scale chain indexers for exchange workloads.
- (decision) Production launch for real customer funds requires explicit environment gates: versioned migrations, structured observability, money-flow SLOs, alerting, incident runbooks, backup/restore drills, and signer/withdrawal audit trails.
- (decision) Existing underscore webhook names such as payment_succeeded remain compatibility aliases until a versioned event catalog migration defines and deprecates them; dotted v1 names are the target convention for new events.
